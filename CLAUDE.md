# GameplayMod

Игровые механики для Minecraft 26.2, Java 25, Fabric (Loom): плавающие брёвна, тарзанки и другое. Id мода и пространство имён — `gameplaymod`, пакет `com.smeshariki.gameplay`. Зависит от `uilib` (общий интерфейс окон, `../UiLib/CLAUDE.md`; сейчас им пользуется только `CharacterChoiceScreen`): собирать UiLib первым. Миры не содержит (они в SmesharikiWorldMod), строительные блоки — в BuildMod; дубли регистраций с ними не создавать.

## Правила работы

- **Проверять поведение в игре клиентским gametest в творческом режиме** (там нет экрана выбора персонажа, блокирующего ввод). Шаблон: копия проекта, `fabricApi { configureTests { createSourceSet = true; modId = ...; enableClientGameTests = true; eula = true } }`, задача `runClientGameTest`; в рабочем проекте тестов нет. Держать контроль: без него нули ничего не значат.
- **После каждой правки:** собрать (`./gradlew jar`) и положить `build/libs/gameplaymod-1.0.0.jar` в `~/.minecraft/mods/gameplaymod-1.0.0.jar`. Копировать только атомарно: `cp` во временный `.jar.tmp` в той же папке и `mv -f` (прямой `cp` поверх jar запущенной игры ломает её). Если сборка не прошла — ничего не копировать и сказать.
- **Статическая инициализация клиентских моделей** (`KroshModel`, `YozhikModel`, `Voxels`): порядок объявления `static final` полей важен — поле, использующее другое через метод, должно идти после него (иначе NPE при загрузке рендереров и чёрный экран при старте игры; сборка этого не ловит). После правок моделей проверять без игры: запустить `Class.forName` на моделях на JDK из `org.gradle.java.home` с classpath из `build/classes/java/{client,main}`, jar'ов Minecraft (`~/.gradle/caches/fabric-loom/minecraftMaven/...`) и библиотек.
- Код: `src/main/java/com/smeshariki/gameplay/` (`GameplayMod` — точка входа и регистрация). Ресурсы: `src/main/resources/assets/gameplaymod/`.

## Сохранение и откат версий

- Состояние лежит в NBT сущностей (верёвка, маркер течения) и сбрасывается вместе с чанками при `saveAllChunks`. Единственный свой файл — маршруты брёвен `data/gameplaymod/log_routes.dat` (`raft/LogRoutes`, SavedData): его пишет скрипт SmesharikiWorldMod при закрытой игре, мод только читает. Данные «только в памяти и на остановку мира» не заводить — в версию они не попадут, а при откате могут перезаписать мир.
- Статическое состояние (`CurrentField`) — только кэш, пересчитываемый по сущностям; чистится при остановке сервера и выходе клиента (`CurrentField.clear()`).
- Откат закрывает мир, новое состояние читается при следующем открытии: течения и верёвки после отката проверять в свежем запуске мира.

## Состояние

- Каркас (2026-10-25): точка входа и регистрация.
- Тарзанка (2026-10-25, проверена в игре): пакет `rope/` — `Ropes` (регистрация, обработчики ПКМ с зажатым концом), `RopeItem`, `RopeEntity` (позиция сущности = свободный конец, крепление в данных; режимы FREE/ATTACHED/HELD; жёсткая верёвка, длина у каждой своя (2–24, по умолчанию 8; меняется клавишами `[` `]` пакетом `AdjustLength`), ограничение только длиной (`correction`/`clipVelocity`; предела угла нет, был 45° — убран по просьбе), маятник на сервере, ограничение игрока на его клиенте). Рендер — `src/client/.../RopeRenderer` (две перекрёстные ленты `RenderTypes.leash()`, с провисом). Упругости пока нет.
- Управление тарзанкой (2026-10-25): всё по ЛКМ через `ClientPreAttackCallback` и пакет `RopeAction`. ЛКМ по верёвке — схватить в любом месте (`RopePicker`: луч взгляда против дуги), рычаг маятника = расстояние от крепления до руки (`ARM`), остаток верёвки свисает из руки; ЛКМ с верёвкой в руке — отпустить (конец падает вниз по хвосту); ЛКМ по самому креплению — сломать (предмет возвращается). ПКМ по блоку с верёвкой в руке — зацепить конец. Сущность не `isPickable`, ударом по ней ничего не происходит. Клавиши `[` `]` меняют длину (и рычаг вместе с ней).
- Захват по клетке и инерция (2026-10-25): `RopePicker` идёт по лучу взгляда и берёт первую клетку воздуха (до стены, досягаемость 4), где есть участок верёвки; участок должен быть не дальше 0,75 от луча (`MAX_MISS`), ближайший к лучу у креплений (<0,5) ломает верёвку. После отпускания `GameplayModClient.keepMomentum` до приземления возвращает игроку горизонтальное ванильное сопротивление (вертикаль ванильная), конец верёвки наследует скорость руки.
- Течение рек (2026-10-25, проверено в игре): пакет `current/` — `CurrentMarkerEntity` (маркер в клетке воды, только курс с шагом 30°), `CurrentMarkerItem` (предмет `current_marker`), `CurrentField` (поле по связной воде: обход в ширину от маркеров до 32 клеток, побеждает ближайший; пересчёт при изменении маркеров и раз в 100 тиков, у сервера и клиента своё), `Currents` (регистрация, `push` — разгон вдоль течения до 10 блоков/с (`SPEED`), цель 1,2×`SPEED` из-за сопротивления воды). Игрока толкает его клиент (`client/CurrentsClient`). Маркер рисуется текстурой значка предмета, плоско в XZ (`CurrentMarkerRenderer`), только пока в руке маркер. Управление: ПКМ по воде — поставить; ПКМ по маркеру — повернуть на +30°; ЛКМ по маркеру — убрать. Силы и маркера остановки нет (убраны по просьбе: течение и так действует только на 32 клетки). Бурление (2026-11-04; проверено клиентским gametest на бассейне 19×19 с контролем без маркера, сверху и из-под воды): течение видно всегда — `CurrentMarkerRenderer` рисует на открытой поверхности воды каждого маркера (`CurrentField.Surface`: клетки воды без воды сверху, высота, свет, таяние на последних 6 клетках к краю поля; считается только у клиента при пересчёте поля) два слоя бегущих по течению завитков `textures/entity/current.png` (гуще ветра: струи, водовороты, пена; бесшовная по обеим осям, сгенерирована скриптом, исходник не хранится), слои `LAYERS` с разным шагом и скоростью; дальше 64 блоков от камеры не рисуется. Текстуры повторяются сами (у `SimpleTexture` REPEAT без `clamp` в mcmeta), поэтому UV берутся в осях течения и стыкуются между клетками.

- Плоты по течению (2026-10-26, проверены в игре): пакет `raft/` — `Rafts` (регистрация, предмет `raft_binder` «Связка плота», сборка/разборка, пакет `RaftBlocks` с блоками), `RaftEntity` (позиция = центр основания; блоки убраны из мира и лежат в сущности, NBT как у `PlatformEntity` из BuildMod; плавает на поверхности воды с осадкой 0,6 (`RaftEntity.DRAFT`; было 0,3, опущено 2026-11-05, чтобы на палубу можно было выбраться из воды — в игре не проверено; палуба в один блок теперь на 0,4 над водой), скорость берёт из `CurrentField` под собой, до `RaftEntity.SPEED` (6,66 блока/с с 2026-11-04, было 10 как у `Currents.SPEED`; тела в течении по-прежнему 10), упирается в блоки мира, несёт стоящих на нём). ПКМ связкой по блоку — собрать в плот связную постройку (до 300 блоков, без блоков с содержимым; с 2026-10-31 вода не нужна, а земля/камень/песок не входят в плот и только ограничивают обход, плот на суше лежит на месте); ПКМ связкой по плоту — разобрать (блоки встают по округлённой позиции, что не помещается — выпадает). Столкновения плота — общий миксин `gameplaymod.common.mixins.json` (`EntityGetterMixin`, `ServerGamePacketListenerImplMixin`, по образцу BuildMod); рендер — `client/RaftRenderer` (движущиеся блоки). Игрока на плоту несёт его клиент, остальных — сервер. Движение `simulate()` считают и сервер, и клиент одинаково (по `CurrentField`, воде и блокам своего мира); позиционные пакеты клиент не применяет (`RaftEntity.setPos` на клиенте только запоминает их), а возвращает плот к присланной позиции лишь при расхождении >3 блоков или при входе в зону (первые 10 тиков берёт скорость из шага пакетов) — иначе плот прыгал по пакетам и уходил из-под игрока.
- Брёвна на реке (2026-11-02; поток, появление на воде и анимация проверены клиентским gametest на геометрии из мира, переход человеком не проверен): пакет `raft/` — `LogRiver` (спавн, типы `log_raft` и билета чанков), `LogRaftEntity` (наследует `RaftEntity`: столкновения, рендер, перенос стоящего — общие), `LogRoute` (маршрут одной реки) и `LogRoutes` (2026-11-04: маршруты в данных мира `data/gameplaymod/log_routes.dat`, пишет `SmesharikiWorldMod/tools/log_route.py`; клиенту приходят пакетом `LogRoutes.Sync` при входе; рек может быть несколько, у бревна номер маршрута `ROUTE`; проверено клиентским gametest: файл мира читается, брёвна по своему маршруту идут у сервера и клиента). Брёвна идут не по полю течений, а по маршруту (в «Ромашковой Долине» маршрут «река» от (357, 140, −187) до (621, 63, −190)): плот застревал на водопаде и на узких местах и не занимал всю ширину реки (13–17 блоков; 4–5 только в начале). Течение на бревно не действует, новые маркеры его не повернут. Скорость 3,33 блока/с (`LogRaftEntity.LOG_SPEED`, своя с 2026-11-04: было 10, потом 6,66 вместе с плотами), на падении вдвое больше, путь около 110 с; частота по времени прежняя, поэтому брёвна идут втрое теснее, чем при 10. Брёвна идут двумя рядами вокруг средней линии (таблица пересчитана 2026-11-02, смещение от середины между берегами по карте мира не больше 0,5 блока, на каскаде к морю x>606 дуга прежняя): у каждого ряда своя половина реки (`CENTERS` ±0,7 размаха) и качание ±0,3 размаха (`SWAY`), один ряд синусоида, другой косинусоида, длина волны 70 блоков (`WAVELENGTH`, `PHASES`). Ряды не пересекаются. Размах — полуширина поперёк линии минус `LogRoute.MARGIN` 3,0. В узких местах размаха нет, и ряды сливаются (x<400 почти везде). Положение зависит от времени старта и этих чисел, сервер и клиент считают его сами; клиент догоняет расчётный путь при расхождении больше 3 блоков. В тесте расхождение достигало 11,93 блока, причина и у каких брёвен не выяснено; столкновения игрока считает клиент, но `standsOnRaft` на сервере смотрит серверные брёвна, поэтому в выживании при долгой езде возможен кик за полёт (не проверено). Формы: 4 по осям и лесенки (45° и пологие), не больше 4 блоков по x и z, из `jungle_log`. Частота: на каждой траектории следующее бревно через случайные 12–36 тиков (`GAP_MIN`, `GAP_MAX`), всего около 1,7 бревна/с и 60 живых. Синусоида (2026-11-02; клиентский gametest со случайными амплитудой и волной, на упрощённых берегах, с двумя рядами не прогонялся: стоящий на бревне держится на месте всю езду, у берега его может перенести на берег; брёвна не сталкиваются и проходят друг сквозь друга; около 1 % точек брёвен в камне берега, на изгибах). По расчёту на таблице при x≥400 для бревна с половиной длины 2: центры рядов расходятся на 1,8–10,6 блока, обычно 5,4 (не меньше 4 на 85 % длины, ряды сливаются только у x≈401–407); в пределах прыжка с места 66–67 % длины берега, с разбега 88–91 %, самый длинный участок вне прыжка 15–21 блок (в игре и человеком не проверено). Частота выбрана для прежних прямых полос и по замеру до инерции плотов (2026-11-02), с ней игрок в воздухе летит вместе с бревном, поэтому числа ниже устарели: прыжок 11 тиков, с разбега 3,63 блока, с места 2,88. Для прежних полос: модель давала 10–22 цепочки в минуту с разбега и 5–14 с места, бот с прыжками с места перешёл 6 раз из 29 при `INTERVAL` 12 и `SKIP` 0,2. Сложность менять `GAP_MIN`, `GAP_MAX`, `CENTERS`, `SWAY`, `WAVELENGTH` и `LogRoute.MARGIN`. Поток идёт, пока игрок в 160 блоках от реки и в мире есть маркеры течения, а начало маршрута — вода с течением; чанки реки держит билет на время (иначе низовья без брёвен). Брёвна не сохраняются (`noSave`), связкой не разбираются. В конце маршрута разрушается (`RaftEntity.destroy`, см. пункт «Разрушение плотов»).
- Сдвиг рядов брёвен (2026-11-04, собрано, в игре не проверено): `LogRiver.SHIFTS` — сдвиг каждого ряда поперёк русла в блоках, плюс к правому берегу по течению (у «реки», текущей на восток, — к югу). Сейчас { −2, 2 }: ряд у левого берега (`CENTERS` −0,7) на 2 к левому, у правого — на 2 к правому (сначала был { 2, 0 }, пользователь поправил). Сдвиг в данных бревна (`SHIFT`), `LogRoute.at(s, lane, shift, out)` ограничивает ось размахом (не ближе `MARGIN` 3 к берегу), поэтому на деле при x≥400 сдвиг около 1 блока (медиана 0,9–1,0), в узких местах 0. Расстояние между осями рядов при x≥400: медиана 7,9 блока (без сдвига 5,4), меньше 4 на 10 % длины. Прежние числа в пункте выше — для рядов без сдвига.
- Третий ряд брёвен (2026-11-04, собрано, в игре не проверено): `CENTERS`/`PHASES`/`SHIFTS` получили третий элемент (0, 0, 0) и новый массив `SWAYS` { 0,3, 0,3, 0 } вместо общего `SWAY`: третий ряд идёт строго по средней линии маршрута, без качания и сдвига. По таблице при x≥400 от средней линии до осей боковых рядов медиана 4,0 (левый) и 3,9 (правый), меньше 3 блоков на 12 % длины; в узких местах все три ряда сливаются (брёвна проходят друг сквозь друга).
